# Server Purchase & Actor Lifecycle

## 지급 성공과 생성 성공

기존 구매는 Actor를 생성한 뒤 반환값이 없는 상호작용을 호출했다. 슬롯 지급·소유권·부착이 끝났다는 확인 없이 성공 응답과 결제가 이어질 수 있었다. 서버가 검증부터 정산까지 수행하되 기존 장비 API를 재사용하는 방향으로 수정했다.

UShopComponent는 구매 구간·생존 Pawn·카탈로그·가격·스택과 아머를 판정한다. 경형·중형 최대 수치의 중복은 거부하고 손상 복구와 업그레이드는 정가다. 미사용 무기는 교체 시 환불하고 사용한 무기는 드롭한다. 클라이언트 표시 판단 후에도 서버가 다시 검증한다.

## 공통 장착과 복구

구매와 일반 월드 획득은 ABaseWeapon::TryEquipWeapon을 사용한다.

~~~cpp
Mesh->SetSimulatePhysics(false);
if (!AttachWeaponMeshes(Agent))
{
    // Restore the original attachment, transform, collision and physics.
    return false;
}
// Ownership and pickup callbacks occur after successful attachment.
ABaseInteractor::ServerRPC_PickUp_Implementation(&Agent);
~~~

일반 획득은 PickUp 이벤트와 소유자 설정이 부착보다 먼저 실행되던 점도 수정했다. 1인칭 부착, 3인칭 생성, 3인칭 부착의 실패를 각각 검사해 이전 슬롯과 월드 무기의 재획득 가능 상태를 보존한다. 구매는 지급이 확정된 뒤 가격과 환불의 차액을 한 번 정산한다. [실제 함수](https://github.com/chungheonLee0325/VALORANT/blob/main/UnrealEngine/Valorant/Source/Valorant/Weapon/BaseWeapon.cpp)

## 요청·응답

RequestID는 Controller 연결별 증가 번호다. 서버는 이미 처리했거나 더 오래된 번호를 재정산 없이 거부한다. 처음에는 처리 중 같은 번호 병합, uint32 래핑 비교, 재진입 잠금까지 두었다. 한 연결의 Reliable 서버 RPC는 한 번씩 순서대로 실행되고, 구매 처리 중 다시 구매를 부르는 C++·Blueprint 경로도 없어 후속 개선에서 제거했다.

번호의 핵심 가치는 클라이언트 UShopViewModel의 대조다. 10초 타임아웃은 대기 표시를 끝내고, 그 뒤 늦게 온 응답은 새 요청을 끝내지 못한다. 서버가 이미 처리한 장비와 잔액은 복제로 반영한다.

## Actor 수명

서버가 만드는 AThirdPersonInteractor는 무기의 종속 표시 Actor이며 Owner는 장착 Pawn이다. 무기 파괴는 EndPlay에서, 드롭은 소유자 해제에서 정리한다. UObject GC의 BeginDestroy까지 게임플레이 정리를 기다리지 않는다. 드롭한 무기는 월드에 남는다.

원격 참조가 아직 없으면 역참조하지 않고 Owner 복제와 메시 데이터 ID로 표시를 갱신한다. 이전에 관찰한 원격 초기화 크래시도 이 경계에서 수정했다.
